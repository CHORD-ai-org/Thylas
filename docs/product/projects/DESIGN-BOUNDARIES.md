## 2. 边界图（谁的事）

```text
Thylas（产品层）        GSC（信息层）          CoworkOS（协议层，未来独立）
├─ A 项目即对象         ├─ D 项目分区(scope)    ├─ G coworker 间协议
├─ B Cluster 归一       ├─ E 署名(治理扩展)     └─ F 交接(协议的一个动词)
└─ C 项目画布           └─ 同步/共享
```

一条红线：**A/B/C 是 Thylas 的体验；D/E 是 GSC 的信息治理；G 是协议（今天借用 CoworkOS，明天独立）；F 落在协议上，但交接的"体验"在 Thylas。**

## 3. 每个边界的展开

### A 项目即对象（Thylas）
- **场面**：`D:\github projects\Thylas` 这个文件夹在 Thylas 里显示为一张"项目卡"——有名字、有摘要、能被评论、能被 `@` 引用、能被 Coworker 当作一个整体接手。
- **不是**：不是把文件夹搬进 Thylas（文件还在磁盘原处）；不是 Artifact 的一种新 kind 的立刻建模——先说清"像 Artifact 的哪几个性质"（可讨论=评论挂项目；可复用=复制成模板/fork/引用？**未定**）。
- **内部问题**：项目身份锚在路径还是名字？路径变了（改名/移动）项目卡跟不跟？一个项目可否同时是另一个项目的子项目？
- **接壤**：B（谁构成它）、C（它怎么被看见）、D（它的信息分区）。

### B Cluster：多文件夹归一（Thylas）
- **场面**：把 `lemma-ai`、`LemmaKnowledgeBase`、`Lemma AI Analysis Engine` 三个文件夹拖进同一个 Cluster，起名"Lemma"。桌面上它们是一张项目卡，磁盘上是三个文件夹。
- **不是**：不是同步工具（不搬文件）；不是 monorepo（不改变文件系统的组织）。
- **内部问题**：链接是引用还是索引？一个文件夹可属多个 Cluster 吗（应可，多对多）？Cluster 内文件夹间的边界怎么读（比如一个放代码一个放文档）？
- **接壤**：A（Cluster 就是那个项目对象的实体）、E（Cluster 内谁写了什么要署名）。

### C 项目画布（Thylas）
- **场面**：打开"我的项目"不是一抽屉列表，是画布：每个项目一张卡，可以摆、连（"这两个项目共用一个引擎"）、圈选、注释——**直接复用空间环境愿景的全部手势**。
- **不是**：不是新的画布引擎——就是 C2 空间环境，把材料卡换成项目卡。
- **内部问题**：项目画布和个人空间是同一张桌子的两个楼层，还是两个空间？（开放）
- **接壤**：空间环境愿景（已暂存，正好接上）、A。

### D 项目 GSC 分区 + 共享（GSC）
- **场面**：项目"Lemma"有自己的 GSC 分区——项目里的笔记、决策、概念都进这个分区；把项目共享给 Moelink，分区跟着共享；他 Coworker 的产出也进同一分区并署名。
- **不是**：不是 GSC 新实体——是 **scope 概念的落地**（现有 GSC scope: personal/workspace；项目分区=项目级 scope）。
- **内部问题**：分区与 workspace scope 什么关系（项目跨 workspace 吗）？共享粒度（整分区 vs 选中的条目）？同步是实时还是拉取？
- **接壤**：E（署名是分区的元数据基础）、B（分区挂在 Cluster 上）。

### E 署名（GSC 治理，针对 Coworker）
- **场面**：分区里一条决策记录写着"由 Mira 提出 · Ceaser 确认 · 2026-11-22"。Coworker 说的每句话、提的每个提案都带名字——不是匿名的"系统说"。
- **不是**：不是 provenance（来源）——provenance 说"信息从哪来"，署名说"**谁**以自己的名义说了/做了"。现有 GSC 有 origin 级（user/agent/machine）但没有**署名级**（哪个 agent、哪个人）。
- **内部问题**：署名是强制还是可选？署名的验证性（怎么证明是 Mira 说的）？署名与权限（署名者对内容负责吗）？
- **接壤**：与 MCS 研究的归因五类（feedback/independent/co-edit/takeover/reuse）同一族问题——**署名是"谁"，归因是"以什么意图"**，两层都要。F/G 都依赖它。

### F 交接（协议的动词，体验在 Thylas）
- **场面**：你圈 12 张卡交给 Mira（这是交代）；Mira 做到一半要下班，把"当前理解 + 已做 + 未决 + 建议下一步"打包交给 Archer——**这就是交接**。Archer 打开时看到的是一份完整工作现场，不是一段聊天记录。
- **不是**：不是消息转发；不是聊天历史导出。
- **内部问题**：交接包含什么（working context + 痕迹 + 授权？）；交出后 Mira 还能改吗（权限转移 vs 复制）；交接记录本身是否留痕。
- **接壤**：home-interaction 的委派设计（D2/D3）、G（交接是协议的一个原语）。

### G CoworkOS 协议（今天借用，明天独立）
- **场面**：coworker 之间的一切协作——交代、交接、署名、请求澄清、交回结果——都走同一套消息格式和状态机。CoworkOS 是这套格式的名字。
- **不是**：不是 agent 运行时（WAM 边界不变：运行时归 WAM，CoworkOS 是**协作协议**）；不是 Thylas 的一部分——"后面要把这个协议单独分离出来"。
- **内部问题**：协议的最小动词集（delegate/handoff/sign/clarify/return？）；与 WAM A2A 的关系（上层协议 vs 替代？**未定**）；独立出去时的归属（独立仓库/规范文档？）。
- **接壤**：F 是它的动词之一；E 是它的头字段；WAM-BOUNDARY 必须重读。

## 4. 撞名与既有资产（先说清，免得两套定义）

| 词 | 撞名 | 裁定建议 |
|---|---|---|
| **Cluster** | GSC 研究里 Cluster = 一组信息对象的分组 | "Thylas Cluster"=文件夹归一（项目实体）是**另一个东西**。改叫 **Project** 或登记为歧义词（待选） |
| **署名** | MCS 术语表已有 Attribution（归因五类） | 署名=actor 身份层，归因=意图层；GSC 补的是署名层，两层共存 |
| **分区** | GSC 的 Context（装配）也是"分区"感 | 项目分区=scope 维度，Context=装配记录，不合并 |
| **CoworkOS** | 全新名 | 先当工作名；与 WAM 的协议边界是 Q1 |

## 5. 依赖顺序（分散后自然出现）

1. **E 署名**先定（D/F/G 全压在它上面，且它最小——GSC 治理加一层）。
2. **A/B 项目对象 + Cluster**（Thylas 侧核心，互相定义）。
3. **D 分区**（依赖 A/B 的实体 + E 的元数据）。
4. **F 交接**（依赖 E + working context 概念——home-interaction Q3 同源）。
5. **G CoworkOS**（动词集随 F 的需要长出来，独立分离放最后）。
6. **C 项目画布**（体验层，依赖 A/B 成形；直接复用暂存的空间愿景）。
