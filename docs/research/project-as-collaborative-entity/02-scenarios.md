## 场景 1 — 本地文件夹连接到新 Project

- **看到**：Workspace 的项目地图（画布）；空处"+ 新建项目"；左侧材料栏有"连接文件夹"。
- **做**：建项目卡"Thylas 产品研究" → 连接 `D:\github projects\Thylas`。
- **系统**：Project 获得 id/名字/Context 分区（GSC project 级 scope）；文件夹只登记**引用**（路径 + 连接器），文件不动；引用可解析（文件夹改名 → 连接器标"路径失效"，项目卡不损坏——锚是 id 不是路径，H1）。
- **边界**：Thylas 管引用登记与呈现；文件真实在磁盘/外部系统。

## 场景 2 — 三个独立 Repository 组织进一个 Project

- **看到**：项目"Lemma"的桌面；材料栏"连接 GitHub"。
- **做**：把 `lemma-ai`、`LemmaKnowledgeBase`、`Analysis Engine` 三个 repo 连进项目，摆卡。
- **系统**：三份引用挂同一 Project；repo 是资源不是项目；Coworker 参工后按授权看到引用（读真身走工具/WAM）。
- **检验**：项目身份独立于任何单一目录——一个 Project 多资源成立。

## 场景 3 — 跨 Workspace 组织项目（重写）

> brief 原场景"创建包含多个 Project 的 Cluster"已随 01 §4 裁定（Cluster=Workspace）重写为本场景。

- **看到**：切换器两个 Workspace（"CHORD" / "个人"）；共享入口。
- **做**：把"读书笔记"项目**共享**给"CHORD"（或反向），对方名册可见。
- **系统**：项目本体属唯一 Workspace；跨 Workspace = 引用/共享（项目 Context 分区可跟共享，按 01 §6-3），不复制；对方 Workspace 名册决定谁可见。
- **边界**：GSC 管共享边与权限，Thylas 管邀请与呈现。

## 场景 4 — 两个 Project 共享部分 GSC Context

- **看到**：项目 A 分区里一条决策"检索管线选型"；项目 B 分区里出现"引用自 A"卡。
- **做**：在 B 里 `@A 的选型决策` 引用 / 把 A 的条目显式共享给 B。
- **系统**：GSC 记 cross-project 引用边，**不复制**；A 更新 → B 引用处显示"已更新"提示；B 的参工者只可读被共享条目（访问控制在 GSC，粒度=条目【提案】）。
- **检验**：共享 ≠ 同步、≠ 复制。

## 场景 5 — Coworker 加入 Project

- **看到**：Workspace 管理面"名册：Mira（研究员）"；项目卡"参与者"区。
- **做**：把 Mira 派进"Thylas 产品"，给角色"研究助理"，勾资源授权子集。
- **系统**：入职层（名册/身份/工具权限）与参工层（角色/子集授权）分离；Mira 只见授权材料 + 项目分区；产出落回项目桌面新卡组（永不覆盖用户排布），署名 Mira。
- **检验**：授权 = Coworker 配置 ∩ Workspace 给予 ∩ Project 子集（三层交集，延续 WORKSPACE-RELATIONSHIP 红线）。

## 场景 6 — Coworker 之间交接

- **看到**：Mira 工作卡组旁"交接"动作；交接包预览（当前理解/已做/未决/建议下一步）。
- **做**：Mira 把包交给 Archer；人可附一句指令。
- **系统**：工作状态包（working context 引用 + 痕迹 + 授权范围）转移给 Archer；留交接记录（交出/接收双方署名）；Archer 打开是完整工作现场不是聊天记录。
- **边界**：交接 = 协议动词（CoworkOS），体验在 Thylas。【开放】交出后 Mira 是失去在办权（权限转移）还是保留（复制）——两案均成立，待 D2。

## 场景 7 — Agent 创 artifact → Agent 修改 → 人类审核

- **看到**：桌面"待审"角标；卡上 Mira→Archer 的修改痕迹，各带一行署名理由。
- **做**：人点采纳/驳回。
- **系统**：走候选→评审→提交管线（现有 `artifactCandidates` 模式，复用）；每步署名（谁提/谁改/谁批）；最终 artifact 带完整 attribution 链。
- **红线**：执行权限 ≠ 提交权（home-interaction MutationIntent 治理）。

## 场景 8 — 项目成果被另一项目引用或派生

- **看到**：项目 B 桌面"引用自 A 的研究报告"卡（A 角标）；右键"引用 / 派生为新卡"。
- **做**：选"派生"，改写成 B 的版本。
- **系统**：派生记 `derived_from` 边（GSC 溯源）；A 改动不覆盖 B 的派生体；引用体始终指向 A 的权威版。
- **边界**：项目"可复用"的最小闭环 = 引用 + 派生先行；整项目模板/fork 后议（O-P3）。

## 场景 9 — 项目归档、转移、删除

- **看到**：项目卡菜单"归档 / 转移 / 删除"；分区归属提示行。
- **做**：归档"Thylas v0 调研"。
- **系统**：卡从地图收进"归档"视图；**Context 分区保留**（生命周期解耦【提案】）；被引用条目仍可解析；参工历史与署名保留；删除 = 软删 30 天（O7 默认）。转移（换 Workspace）先做授权闭合检查（名册/工具授权对齐，默认⑥）。

## 场景 10 — 一个本地文件夹被多个 Project 引用

- **看到**：`D:\github projects\GSC` 详情标"2 个项目引用"（GSC 接口 / Thylas 产品）。
- **做**：在项目 A 里改文件（磁盘上真实修改）。
- **系统**：两项目引用同一真实文件（一致性天然成立）；一方要"独占修改"时【开放】——默认 Thylas 体验层提示，仲裁在文件系统/Git（O-P7）。
