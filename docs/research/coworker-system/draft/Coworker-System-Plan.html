Part I · 参与者，不是聊天窗

1. 从一个场面开始

你说"把这 12 张卡交给 Mira"。Mira 做到一半要下班，把"当前理解 + 已做 + 未决 + 建议下一步"打包交给 Archer。Archer 打开时看到的是一张完整工作现场，不是一段聊天记录。

今天软件里的"AI 助手"是每场对话重新开始的聊天窗。你要的是长期共事的同事：认识项目、记得上次干到哪、以自己的名义署名、能被交接。

2. Coworker 的六条构成【直觉】

构成一句话
独立身份名字、头像、角色——"Mira 是研究员"
职责与边界负责什么、不负责什么、交付什么
Mind Framework它怎么拆任务、组织上下文、处理不确定性——不是一段 system prompt
Methodologies它做某类工作的具体方法（文献综述 / 黑盒分析 / 假设检验）
授权环境可用的 Workspace、材料、Artifact、工具——逐项授予，不默认全给
工作历史持久的参与记录——干过什么、署过什么名

3. 两层制（与 Project 模型对齐）【提案】

层动作内容
Workspace 级 = 入职管理 Coworker 进入名册、身份、工具权限
Project 级 = 参工派进项目角色、资源子集授权、参与历史、产出署名

授权红线【事实】：有效授权 = 自身配置 ∩ Workspace 给予 ∩ Project 子集。三层交集，永不放宽。

Part II · 概念模型

4. 领域对象【提案】

对象职责不负责
Identity名字、描述、角色、领域、视觉身份外貌即身份——身份是工作身份
Responsibilities责任范围、显式排除、期望交付不与能力/方法混为一谈
Mind Framework拆解任务、组织上下文、推理、评估证据、选择方法、求助与协作方式不是自由文本 prompt
Methodology可复用的方法定义（Methodology / Method Run / Result / Evaluation 四分）单次执行是 Method Run，不是方法本身
Toolsets可调用的能力面与职责/心智/方法严格分开
Working Experience参与历史、署名记录、可被复盘不做人事考核

渐进演化：不必一次配齐——方法可后加、Mind 可修订、职责可扩、权限可调（重要变更走版本化 + 显式授权）。

5. 与其他对象的关系【提案】

对象关系
Workspace入职（名册/工具授权）；Coworker 跨 Workspace 独立存在
Project参工（角色/子集/署名）；参工历史留在项目里
Artifact发现、理解、引用、执行、产出、提议修改——Mind 与 Methodology 未来可沉淀为 Artifact
GSCContext 分区的读写按授权；署名层是 GSC 现缺的一层（origin 级只有 user/agent/machine）

Part III · 协作模型 ← Q-A 裁决点

6. 三个方向【提案】

  • H2A：人 → Coworker（交代、圈选即工单、干预、审批）
  • A2H：Coworker → 人（请示、汇报、请求澄清、提交成果）
  • A2A：Coworker ↔ Coworker（委派、交接、质疑、协商、成果交换）

功能性红线【直觉】：多 Coworker 不是各说各话再拼接。必须有共享上下文、任务委派、结构化成果交换、质疑与回应、交接、人类干预，且全程可追溯（谁发起/给了什么/期望什么/实际产出/是否被接受）。

7. 协作机制放哪【已裁 2026-11-24】

本阶段裁定：本地闭环。 协作最小闭环用本地确定性协调器，跑在现有 /api/ai 真实编排管线上；WAM 对接降为"未来兼容层"——不进本阶段范围、不设依赖。

历史方案内容处置
(a) 纯契约Thylas 只做痕迹/渲染契约，A2A 归 WAM未来对接时回看
(b) 本地协调器Thylas 内置确定性协调器跑通最小闭环本阶段采用（轻量版：只做协作原语的状态机，不做通用编排）

红线不变：不做装饰性多智能体；全程可追溯。

8. 协作原语候选（本地闭环状态机的动词）【提案】

Request · Delegate · Respond · Challenge · Negotiate · Handoff · Request Human Input · Approve/Reject · Complete。

交接包 v0（S1 默认复制+留痕）：当前理解 + 已做 + 未决 + 建议下一步 + working context 引用 + 授权范围 + 双方署名。

Part IV · 创建与成长

9. 创建 = Commissioning【提案】

建立一段工作关系，不是填配置表。六阶段（叙事层）：Intention（自然语言描述意图）→ Identity → Responsibilities → Mind & Method → Environment（授权）→ First Encounter（第一次实测）。实施规划见 §28。

Q-C【开放】：六阶段是覆盖在现有一页六区（CoworkerNew）上的叙事，还是替换 IA？向导改造计划见 CREATION-WIZARD.md（仅文档）。

10. 成长【提案】

  • 方法可增改、Mind 可修订、职责可扩展、工具可追加。
  • 重要配置变更版本化 + 显式授权；不做失控的自我修改。
  • 从被审核的工作经验中学习（reviewed experience），不从全部历史自学。

Part VII · 技术底座：效果与性能

2026-11-24 技术调研结论（多智能体编排实证 + 协作协议格局），保证上面的设计本地可跑、可快、可负担。调研全文见 tech-research.md。

16. 效果从哪来【提案，实证支撑】

  • 单人优先：能一个 Coworker 干的不拆两个。多智能体典型开销 3–10× token；每次交接都有损。
  • 拆分沿上下文边界，不按职位名：正当拆分只有三种——上下文隔离（约 >1k token 噪声产出）、真并行、专门化；外加独立校验（不见构建过程的评审者）。
  • 生成-校验回路：给 rubric 不给感觉（"每个数字有引用"）；硬上限 2–3 轮；校验者用更便宜的模型。
  • 交接 = 结构化 JSON：任务 / 输入引用 / 输出 schema / 步数上限 + 双方署名。交接包 v0 按此定形，禁止自由聊天式交接。
  • 先建 trace，再建第二个 Coworker：每个协作边界一条结构化记录，可回放。

17. 性能与成本预算【提案】

预算项红线
拓扑hub-and-spoke（协调器居中）；禁全 mesh（N² 通信）、禁递归 spawn
模型分层判断（采纳/驳回/裁决）= 强模型；执行/抽取 = 小模型（实证省 32% 成本不失效果）
成本上限每场协作步数 / token / 秒，协调器强制——不信模型自觉
延迟体验对话抽屉首响快；桌面永不冻结（产出异步落回）；单次委派可见进度
淘汰线协调消息不产出用户价值的，删

实证锚点：层级 supervisor-worker = 97.7% 效果 @ 60.9% 成本（万份文档基准）。

18. 协议层参考（CoworkOS 的坐标）【提案】

协议边界借鉴不借
MCP模型 ↔ 工具工具接入方式不管 agent 间协作
A2A智能体 ↔ 智能体任务状态机（INPUT_REQUIRED / AUTH_REQUIRED）= 审批链骨架；Task/Message/Artifact 结构AgentCard 握手 token 膨胀
ACP企业 REST 互操作——已收敛向 A2A（2026-05），不押注

CoworkOS 动词 ↔ A2A 状态机映射：delegate = Task 创建；Request Human Input = INPUT_REQUIRED；Approve/Reject = AUTH_REQUIRED 解闸；Handoff = Task 转移 + Artifact 交付；Complete = 终态。

协议只搬消息：持久上下文/权限/审计归 Context 层——CoworkOS 不做记忆（印证 GSC/分区边界）。

19. 反模式黑名单【提案】

开放式 agent 聊天（"讨论到达成为止"）· 递归 spawn · 按职位拆 agent（manager/researcher/writer 图好看）· 共享自由文本记忆 · 盲聚合（拼接输出不做综合）· ring leadership（全员都要会规划）。

Part VIII · 技术路径

2026-11-24 文献脑暴（记忆架构四分层 / LangGraph 持久状态机模型）：用什么造、分几层、什么不引。

20. 三层形态【提案】

一个 Coworker = 三层：

层内容载体
配置面Identity / Responsibilities / Mind / Methodologies / ToolsetsPG 表 + JSONB（coworkers）
运行面Method Run = 状态机执行实例；协作原语 = 状态迁移自研轻量运行时（§23），跑现有 /api/ai 管线 + SSE 流回
记忆面Working / Episodic / Semantic 三分（§22）交接包 + coworker_events + Context 分区

数据流：Thylas UI（React）→ /api/coworkers | projects | events（Drizzle/PG）→ 协调器（状态机）→ /api/ai 管线 → SSE 流回桌面。

文献锚：agent = policy + memory + tools + control loop；记忆四分层（CoALA）。

21. Mind 与 Methodology 的技术表示【提案，Q-D 落点】

  • Methodology = 程序性记忆（procedural）：声明式工作流——steps + 条件分支 + 工具需求 + 输出 schema，存 JSONB。Method Run = 状态机实例：typed state + 节点函数 + 条件边 + 每步 checkpoint（LangGraph 的模型：持久执行、可中断、可回放）。
  • Mind = 装配配置：拆解偏好 / 证据标准 / 求助条件 / 方法选择策略 → prompt 装配 + 决策字段。配差异化验证：同一任务两个 Mind 盲测，行为差异可观察才算数。
  • 渐进加载：Methodology 文本按需装入 working memory（常用方法常驻），控制上下文预算——对应文献的"技能式程序记忆 + 蒸馏"。
  • 取舍：不引 LangGraph 框架——我们的状态机是固定小集合、deps 纪律优先；借语义不借依赖（typed state / checkpoint / interrupt 自研 ~轻量实现，LangGraph.js 作参照）。

22. 记忆与上下文三分【提案】

记忆层我们的载体要点
Working交接包 + 结构化 scratchpad（objective / verified_facts / blockers）只装当前任务；大对象存引用不存内容
Episodiccoworker_events（append-only）+ 事后蒸馏的 Episode 摘要时间衰减检索；重放与审计的来源
SemanticContext 分区（决策 / 偏好 / 领域事实）长期；由 episodic 蒸馏而来
  • 蒸馏步：episodic → semantic 定期 consolidation——防 context rot（文献：堆上下文 = 退化 + 延迟 + 成本三杀）。
  • 遗忘分级：决策/署名类长留；调试噪音类限期裁剪（如 30 天）。
  • 边界不变：协议不存记忆（CoworkOS 只搬消息）；语义记忆归 Context 分区——与 GSC 愿景同一层。

23. 技术选型【提案】

关注点选择理由
状态机运行时自研轻量 TS（typed state + 节点 + 条件边 + journal checkpoint）固定小集合；参照 LangGraph 语义，不引依赖
持久化PG/Drizzle：coworkers（JSONB）· events · run checkpoints已有栈
流式SSE（复用 chat stream 模式）已有
结构化输出schema 校验 + 重试 ≤2实证锚点
模型路由判断=强模型、执行=小模型（配置化）Part VII
评测golden journeys + rubric 裁判 + Mind 差异盲测§31

风险注记（文献踩坑清单）：checkpoint 必须存全量状态（只存对话会丢工具态）；非确定性节点（随机/时钟/外部 API）必须在 checkpoint 捕获；条件边不要滥用（每边都条件 = 无法推理的状态机）。

24. 云架构前瞻（本阶段不做，现在留缝）【提案】

原则：本阶段全部本地实现；但每个持久实体满足可迁云端四条——稳定 id、无本机绝对状态、可序列化导出、多租户键位预留。

今天（本地）云端时变化现在留的缝
PG 单库多租户隔离workspace_id 维度已在所有表
/api/ai 本地管线云端模型服务 / 远程 runtime协调器与 runtime 解耦（状态机无本地状态、节点纯函数）
local-folder 连接器（绝对路径）存储键 / 对象存储引用kind + locator 抽象已通用（P0-3）
单用户 session账号 / 成员 / 组织workspaces scope=personal\org 已在
SSE云端流式通道（WS/轮询）流式是传输层，不进状态机
事件 trace 本地库同步 / 归档append-only 事件天然可同步
  • Q-E 更新：云前瞻下"表"默认更强（文件方案云端难迁移）。
  • 不做：多租户实现、云部署、计费——只留缝。

Part X · 执行保证：交互与落地

"百分百执行"不是靠盯，是靠机制。两层保证：设计→实现不走样，运行时交互不丢不错。

28. 创建 Coworker 的分步规划【提案】

创建 = Commissioning 走查：有仪式感的入职面谈，不是 SaaS 配置表。向导六步（叙事层），每步可退出保留草稿：

步用户做什么系统产出跳过策略

29. 设计 → 实现：不走样【提案】

机制做法
契约即规格wire contract（src/lib/*）双端编译错误；每条 API 带 route 测试——文档里的字段就是代码里的字段
门禁 = 自动化断言每个阶段 gate 不做主观判断，写成测试（P0 的 H1 链是模板：连接→改名→标失效→修复全断言）
验收脚本C0–C4 各配一份验收脚本（自动为主、走查为辅）；全绿 = 执行完成的定义
未决截止机制Q-C/Q-D/Q-E 各带默认方案 + 截止触发：到期未裁则默认自动生效——未决漂移是"计划死掉"的第一死因
范围冻结新需求进修订记录不进当期；防 scope creep 吃掉执行
走查清单文案预算 + UI 检查表（13.4 式）上线前逐条过

30. 运行时交互：不丢不错【提案】

机制做法
状态机 + 先落库协作原语 = 状态迁移；每步先写 append-only 事件再执行——崩溃可恢复、可回放
幂等 + 重试上限重试 ≤ 2（实证锚点）；超限进"待人工"，不静默失败
交接原子性交接包快照落库 + 双方署名原子写入；失败 = 交接未发生，不存在半交接
人工兜底任何环节卡住 → 浮出 INPUT_REQUIRED 状态给用户（A2A 状态机借鉴）——永远有人可介入
可回放每步输入输出入 trace——"是否按设计执行"事后可审计，不靠回忆

31. 验证环节：模拟用户交互【提案】

自动化断言可能"全绿但体验是错的"。每单元过三道模拟：

手段做法抓什么
旅程脚本（e2e DOM）headless 浏览器走完整旅程（ui-checks.mjs 模式）：雇 Coworker → 入职 → 派工 → 署名落回 → 交接 → 归档，每步 DOM 断言界面真的响应、状态真的变了

对抗性旅程错误路径必走：断网、半交接回滚、越权访问、连接器断链、连点与中断失败态的一行字反馈、恢复路径真的存在
  • 通过标准：旅程 × 断言矩阵全绿；三元组与设计零偏差；错误路径全部有预算内文案反馈。
  • 节奏：每单元门禁后跑相关旅程；发布前全量。
  • 产出物：journeys.md（旅程清单）+ 偏差记录——发现偏差二选一（改设计或改实现），不留"已知问题"。

32. 100% 执行的定义【提案】

同时满足四条：①C0–C4 验收脚本全绿；②运行时可靠性断言全过（状态机无空洞态、交接原子、重试有上限）；③决策表无"待裁"悬空（已裁或已触发默认）；④模拟用户旅程矩阵全绿、偏差清零。
